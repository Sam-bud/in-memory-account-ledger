# REJECTED.md

## Part A — Acceptance criteria evaluated

The assessment states some of the 8 listed acceptance criteria are incorrect. Each evaluated below.

| # | Criterion | Verdict | Reasoning |
|---|---|---|---|
| 1 | Day 2 closing balance (evaluated end of Day 5, pre-fee) is AED -370.00 | **NOT INDEPENDENTLY VERIFIED** | Simple arithmetic (E1+E2+E7 = -370) supports this, but a fully confident verdict depends on resolving AMBIGUITIES.md #4 (whether "closing balance" for a given day means live-at-the-time or fully hindsight-corrected) and #1 (processing order). We deliberately did not force a resolution to these beyond what was needed to build the system, and are not asserting false confidence on this criterion as a result. Implementation follows the interpretation in AMBIGUITIES.md #4/#1; this criterion has not been separately, independently proven against that implementation via a dedicated test. |
| 2 | E7 causes exactly one overdraft fee, on Day 2 | **NOT INDEPENDENTLY VERIFIED** | Whether a negative-balance condition spanning multiple days would trigger one fee or several per-day fees was not traced day-by-day across the full window with fee-assessment wired in. Our `RuleEngine.assessOverdraftFee` design (called once per day, per account, independently) would naturally charge a fee on every day that day's own closing balance is negative — which could mean more than one fee if the negative condition persists across consecutive days. We have not run this specific trace to confirm the outcome for this exact dataset. |
| 3 | Day 4 settlement of Auth-A must be accepted | **CORRECT** | Verified directly by `FullEventStreamReplayTest.criterion3_day4SettlementOfAuthA_isAccepted()` — passing. Partial settlement (185 against a 200 hold) is not forbidden by any stated rule. |
| 4 | Any settlement referencing an authorization ID not present in the ledger must be rejected, funds must not leave the account | **CORRECT** | Verified directly by `FullEventStreamReplayTest.criterion4_settlementWithUnknownAuthId_isRejected()` — passing. E6 (Auth-Z, no prior authorization) is rejected and never appended to the store. |
| 5 | If Auth-B is approved, its hold reduces available balance but not ledger balance | **CORRECT IN PRINCIPLE, BUT AUTH-B IS NOT ACTUALLY APPROVED IN THIS DATASET** | See AMBIGUITIES.md #8. Auth-B (E8) is correctly rejected by Rule 5, evaluated honestly at the moment it arrives (ledger balance is already negative due to E7's backdated debit, applied earlier in list order). The underlying rule this criterion describes — a hold reduces available balance, not ledger balance — is verified as TRUE in general via an isolated test (`criterion5_activeHold_reducesAvailableBalance_notLedgerBalance`), but the specific premise "if Auth-B is approved" does not occur in this dataset as processed. |
| 6 | After E9, all balances and fees return to their pre-E7 values | **REJECTED** | E9 reverses E7's balance contribution (verified: `AccountLedgerStoreTest.closingBalance_excludesEventReversedByLaterReversal`). However, IF a Day 2 overdraft fee was triggered by E7 (see criterion #2, not independently verified), that fee — once booked — is a separate, permanent, append-only ledger entry. Nothing in the given event stream reverses the fee itself; E9 only references E7. Under Rule 4 (append-only), a booked fee cannot be un-booked by a reversal that doesn't reference it. Therefore "all fees return to pre-E7 values" would be false if a fee was indeed triggered — this criterion is rejected on that basis, contingent on criterion #2's unresolved outcome. |
| 7 | The three BHD instalments in E10 must each be BHD 3.334 | **REJECTED** | 3 x 3.334 = 10.002, not 10.000 (the stated total). Arithmetic contradiction — verified in `FullEventStreamReplayTest.criterion7_bhdInstalments_sumToExactlyTenThousand()`, which confirms the three instalments (implemented as 3.333/3.333/3.334) sum to exactly 10.000, not 10.002. |
| 8 | If the rounded daily interest accruals do not sum to the capitalized total, the remainder is discarded | **REJECTED** | Directly contradicts the spec's own non-negotiable rule: "the rounded daily accruals must sum exactly to the capitalized total." Discarding a remainder is the opposite of enforcing an exact match. Our implementation instead throws `IllegalStateException` if the sums do not match (`RuleEngine.verifyInterestReconciliation`, verified in `RuleEngineTest`) — silent discarding is never performed. |

**Note on criteria #1, #2, #6**: we chose not to force confident verdicts on these by inventing resolutions to ambiguities the spec leaves open (see AMBIGUITIES.md #1, #4, #5). Doing so would mean asserting certainty we don't have. The system is built and tested against the interpretations we did commit to (documented in AMBIGUITIES.md), but a full day-by-day trace specifically confirming criteria #1/#2/#6 against those interpretations was not completed as part of this submission.

## Part B — Implementation approaches considered and abandoned

1. **`LedgerEvent` as one class with nullable fields** (e.g., a single class carrying `authId`, `referencedAuthId`, `referencedEventId`, all nullable depending on event type) — rejected in favor of a sealed interface with one record per event type. Reasoning: type safety (a `CREDIT` event cannot accidentally carry an `authId`), and Java 21's pattern matching over sealed types forces every event type to be handled explicitly wherever the type is switched over.

2. **Raw `List`/`Map` exposed directly to callers for ledger storage** — rejected in favor of the purpose-built `AccountLedgerStore` API (`appendEvent`, `getClosingBalanceAsOf`, `getActiveHolds`, `getAllEvents`). Reasoning: avoids duplicating balance-calculation logic across `RuleEngine`, `HoldManager`, and report generation; enforces the append-only constraint structurally (no `update`/`delete` method exists) rather than by convention.

3. **Caching or incrementally-maintained balance state in `AccountLedgerStore`** — considered, rejected as premature optimization for this dataset's scale (10 events, 6 days, 2 accounts). `getClosingBalanceAsOf` recomputes from the full event list on every call. Simplicity and guaranteed correctness were prioritized over performance that isn't needed here.

4. **Mutating `ActiveHold` status in place** — rejected in favor of deriving hold status fresh on each `getActiveHolds` call (checking whether a settlement/reversal references the authorization), rather than maintaining and mutating a stored status field. Keeps the append-only principle intact for derived state, not just the raw event log.

5. **Externalizing rule constants (overdraft fee amount, interest rate, currency precision) into a JSON/properties config file** — considered, rejected for this exercise. The spec provides fixed, non-negotiable values with no requirement for runtime configurability. Introducing config-loading infrastructure (parsing, missing-file handling, schema validation) adds complexity that doesn't serve correctness here and isn't rewarded by the stated grading criteria. Constants are defined directly in `RuleEngine` and separately justified in `NUMBERS.md`.

6. **`SettlementHandler` initially scanned full event history (`getAllEvents()`) to validate a settlement's referenced authorization** — corrected mid-build to use `AccountLedgerStore.getActiveHolds()` instead, which already excludes closed (settled/reversed) authorizations. The corrected version is simpler and automatically handles "settlement against an already-closed authorization" correctly, without extra code — a case the original approach did not handle at all.

7. **A retry/pending-authorization mechanism for a rejected AUTHORIZATION** (e.g., queuing Auth-B to retry once balance recovers) — considered when reasoning through hypothetical scenarios during design discussion, explicitly not built. No event type in the given stream represents this, and building it would mean inventing functionality beyond what the spec defines. See AMBIGUITIES.md #11.

8. **A speculative "flag or unwind" mechanism for an authorization/settlement lifecycle invalidated in hindsight by a later backdated event** (see AMBIGUITIES.md #9) — considered, explicitly not built, for the same reason as #7 above.
