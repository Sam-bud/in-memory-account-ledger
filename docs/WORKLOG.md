**[Entry 2]** — Data model complete: sealed `LedgerEvent` interface with 5 per-type records (Credit/Debit/Authorization/Settlement/Reversal), `Account`, `Currency`, `HoldStatus`, `ActiveHold`, and `AccountLedgerStore` (purpose-built per-account store with `appendEvent`, `getClosingBalanceAsOf`, `getActiveHolds`, `getAllEvents`). Resolved REVERSAL handling in `getClosingBalanceAsOf`: a reversal excludes its referenced event's contribution from the sum, gated by the reversal's own valueDate. `getActiveHolds` matches a reversal/settlement's reference against both authId and eventId, since the spec doesn't specify which convention applies.

**[Entry 3]** — `RuleEngine` implemented: `isAuthorizationApprovable` (Rule 5), `assessOverdraftFee` (Rule 1, with a `feeFlag` field added to `DebitEvent` to structurally prevent double-charging the same day — checked against real event data, not an ID-string convention), `calculateDailyInterest` + `calculateCapitalizedInterest` + `verifyInterestReconciliation` (Rule 2 — daily figures rounded per-currency, summed, verified to match rather than adjusted/forced to match).

**[Entry 4]** — `HoldManager`, `SettlementHandler`, `ReversalHandler` implemented as thin coordinators, deliberately reusing `AccountLedgerStore`'s existing query methods (`getActiveHolds`) rather than re-scanning raw event history — corrected `SettlementHandler` mid-build after realizing an early draft redundantly scanned `getAllEvents()` instead of using the already-built `getActiveHolds()`. Known, documented redundancy left in place: `RuleEngine.isAuthorizationApprovable` and `HoldManager.getAvailableBalance` both independently sum active holds — not refactored to share one implementation, per scope discipline (simple over polished).

**[Entry 5]** — `DailyReportGenerator`, `EventProcessor`, `EventStreamFactory`, and `Main` implemented. Real design decision made: events are replayed in given LIST order (arrival order), not value_date order — confirmed this matters concretely, not just theoretically, once E8 (Auth-B) was tested (see Entry 7). Errors (rejected settlements/reversals/authorizations) print inline during replay via System.out, not collected and attached to a later per-day report — a real, acknowledged design choice, not the only valid one.

**[Entry 6]** — Full unit test suite written: `AccountLedgerStoreTest`, `RuleEngineTest`, `SettlementHandlerTest`, `ReversalHandlerTest` — all passing on first correct run (after fixing a missing `testRuntimeOnly 'org.junit.platform:junit-platform-launcher'` dependency required by the Gradle version in use).

**[Entry 7]** — Built `EventStreamFactory` with the real E1-E10 data (E10 split as 3.333/3.333/3.334 — a deliberate, documented choice among several valid remainder distributions, not the only correct one) and `FullEventStreamReplayTest` covering criteria #3, #4, #5, #7, #8. First run: `criterion5` FAILED. Root cause investigated with temporary debug logging (since removed): Auth-B (E8, hold 90.00) was being rejected by `isAuthorizationApprovable`, because by the time E8 is evaluated (Day 5, after E7 has already been appended per arrival order), the account's ledger balance is genuinely −155.00 (E7's backdated −620.00, value_date=Day 2, already retroactively applied). This is CORRECT behavior per Rule 5, evaluated honestly and sequentially — not a bug. The original test's assumption that Auth-B should be approved was wrong. Rewrote `criterion5` to use an isolated, minimal scenario (fresh store, single credit + single hold) to cleanly demonstrate "hold reduces available balance, not ledger balance" without the full stream's backdating complexity entangling the assertion. All 5 tests pass after the fix.

**[Entry 8]** — This session is direct, concrete evidence for AMBIGUITIES.md #12/#13 (hold approval decisions evaluated in real-time against whatever balance exists at that exact moment, not retroactively revisited) — it went from a theoretical ambiguity we'd only discussed, to something that actually changed a test's expected outcome once real code was run against real data.
